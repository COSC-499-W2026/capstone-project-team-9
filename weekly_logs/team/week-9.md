# Weekly Team Log

This week, we decided to focus on connecting the different components of our system, improving the overall game loop, implementing authentication, and refactoring the backend architecture to use dependency injection. The goal was to bring the project closer to a usable game for the demo, by allowing players to authenticate, start a game, interact with clues, submit answers, and track their progress.

----
The work was distributed so that:
- **Joe** focused on connecting the play, answer-checking, and game loop logic. This included implementing an endpoint to retrieve the current progress of a play PR [#233](https://github.com/COSC-499-W2026/capstone-project-team-9/pull/233) and connecting answer submission to individual plays, allowing players to complete rounds by correctly answering all clues PR [#236](https://github.com/COSC-499-W2026/capstone-project-team-9/pull/236).

- **Ian** focused on refactoring the backend to use dependency injection and class-based services and repositories. This included converting the location service into a class and injecting it into dependent components PR [#237](https://github.com/COSC-499-W2026/capstone-project-team-9/pull/237), converting the game and game options repositories into classes and injecting them into their respective services PR [#241](https://github.com/COSC-499-W2026/capstone-project-team-9/pull/241), and introducing just to simplify commonly used development and testing commands PR [#244](https://github.com/COSC-499-W2026/capstone-project-team-9/pull/244), and converting the play repository into a class and injecting it into PlayService PR [#254](https://github.com/COSC-499-W2026/capstone-project-team-9/pull/254).

- **Eric** focused on developing the frontend gameplay experience and allowing users to submit photos as answers. This included implementing the play setup interface, clue screen, progress display, and game navigation PR [#249](https://github.com/COSC-499-W2026/capstone-project-team-9/pull/249), as well as implementing camera capture and connecting photo and location submissions to the backend answer-checking endpoint PR [#251](https://github.com/COSC-499-W2026/capstone-project-team-9/pull/251).

- **Nash** focused on implementing authentication and user roles. This included implementing OAuth2 authentication with encrypted JWT access tokens, allowing users to log in and access protected endpoints PR [#242](https://github.com/COSC-499-W2026/capstone-project-team-9/pull/242), and introducing role management with support for students, instructors, and administrators PR [#250](https://github.com/COSC-499-W2026/capstone-project-team-9/pull/250).

We considered alternative workload distributions, such as having everyone work on separate frontend or backend components, or assigning all integration-related work to one team member. However, we decided to distribute work according to the components each member had previously developed or was most familiar with. This allowed Joe and Eric to work closely on connecting the game loop and frontend, while Ian and Nash could independently improve the backend architecture and authentication functionality. This distribution also reduced the likelihood of multiple team members making conflicting changes to the same components.

----
Based on the successful merging of the listed pull requests, the addition of corresponding tests, and manual end-to-end testing, we made progress toward our goal for the demo. The project now has a functioning, very basic game loop. Players can select game settings, start a play, view clues, take photographs of room signs, submit answers with their location, receive feedback, and progress through a round until completion. The backend also supports retrieving play progress, which provides the foundation for saving and resuming game sessions. Authentication and role management have also been implemented, and several backend components have been refactored to support dependency injection.

----
In particular, Joe's PR [#233](https://github.com/COSC-499-W2026/capstone-project-team-9/pull/233) and PR [#236](https://github.com/COSC-499-W2026/capstone-project-team-9/pull/236) connected play progress and answer verification. Previously, answer verification was handled independently of an active play. The new implementation records attempts against individual clues within a play, updates the play's progress when a clue is solved, and marks the play as completed when all clues have been answered correctly. Eric's PR [#249](https://github.com/COSC-499-W2026/capstone-project-team-9/pull/249) and PR [#251](https://github.com/COSC-499-W2026/capstone-project-team-9/pull/251) then connected these backend capabilities to the frontend, allowing the player to interact with the game rather than relying entirely on API requests.

Ian's dependency injection work also progressed further with PR [#254](https://github.com/COSC-499-W2026/capstone-project-team-9/pull/254), which converted the play repository into a PlayRepository class and injected it into PlayService. This continues the broader effort to convert repositories into classes and makes the play service less dependent on the specific implementation of its repository. Existing tests were also updated to accommodate the new structure. However, PlayService still depends directly on the database session because the answer service has not yet been converted into a class.

Some components still require further integration and refinement. For example, clue audio is currently a placeholder, skipping clues has not yet been implemented, and additional functionality such as hints and scoring remains outstanding. Authentication has also been implemented separately from role-based authorization, meaning that although the system can identify a user's role, it does not yet restrict endpoints according to that role. We plan to address these remaining issues during midterm break, along with improving testing consistency and completing the architectural documentation.

The team collectively reviewed the new components and interfaces to reduce the risk of duplicated logic, unnecessary dependencies, and changes in one component requiring changes elsewhere. We spent extra time reviewing PR's as our Github testing currently is not working, so we were sure to run all tests on out own computers before merging.

**Improving separation of concerns:** Joe kept play progress and answer submission logic within PlayService, while leaving OCR and location verification within their respective services PR [#236](https://github.com/COSC-499-W2026/capstone-project-team-9/pull/236). Eric also separated camera functionality into a reusable CameraCapture.vue component rather than placing all camera logic directly inside the clue screen PR [#251](https://github.com/COSC-499-W2026/capstone-project-team-9/pull/251). Nash separated authentication functionality into core/security.py, allowing token generation, validation, and retrieval of the authenticated user to be handled independently of individual endpoint implementations PR [#242](https://github.com/COSC-499-W2026/capstone-project-team-9/pull/242).

**Reducing dependencies between modules:** Ian's PR [#237](https://github.com/COSC-499-W2026/capstone-project-team-9/pull/237) introduced a class-based LocationService and defined it as a dependency in core/dependencies.py. This provides a clearer way for other components to access location functionality. His PR [#241](https://github.com/COSC-499-W2026/capstone-project-team-9/pull/241) converted GameRepository and GameOptionsRepository into classes and injected them into the services that require them. He continued this refactoring in PR [#254](https://github.com/COSC-499-W2026/capstone-project-team-9/pull/254), converting the play repository into PlayRepository and injecting it into PlayService. Together, these changes reduce direct dependencies between services and database operations and make it easier to substitute dependencies during testing.

**Improving testability:** Ian identified that some existing unit tests were testing multiple components together rather than isolating the logic of individual services. His dependency injection refactoring provides a foundation for properly mocking dependencies in unit tests. He also added TODO comments and created Issue #243 to track the remaining work required to improve mocking. The location router tests were updated to mock and override the location service dependency, providing an example of the intended testing approach.

Although these changes improve modularity, we have identified that many changes still require modifications across multiple components. The dependency injection refactoring is intended to address this problem, but it has not yet been applied consistently throughout the entire codebase. We are therefore in the process of improving this through the broader dependency injection refactoring project. We plan to continue this work during midterm break and standardize how dependencies are initialized, injected, and mocked across the application.

With everyone's newly merged work for this week, the system DFD looks largely the same in its current documented form, although the actual data flow has changed. The diagram needs to be updated to reflect the new game loop and answer submission process. 

We considered keeping answer verification as an independent process outside the play system, as it was previously implemented. However, connecting answer submissions to individual plays provides a more consistent way to track attempts and progress, and supports the save-game-state requirement. We also considered having the frontend independently manage game progress, but decided that the backend should remain responsible for determining which clue is current and whether a play has been completed. This prevents the frontend from becoming the source of truth for game state.

----
With everyone's newly merged work for this week, the system architecture diagram also remains unchanged in its current documented form and requires an update. 

We considered keeping the existing function-based service and repository structure, but decided that converting these components into injectable classes would improve modularity and make unit testing easier. We also considered allowing services to instantiate their own repositories and dependencies, but this would make it more difficult to isolate components during testing. Instead, dependency injection allows dependencies to be replaced with mocks without requiring changes to the underlying service logic. This refactoring is still in progress, so the architecture diagram will need to be updated again as more components adopt the pattern.
