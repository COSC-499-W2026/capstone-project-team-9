## Meetings

- Meeting times: Wednesdays (11AM \- 1h)  
- Meeting/Communication frequency:  
  - 1 regular meeting/week to start  
  - 2 lecture times  
  - Discord communication: when help is needed, when PRs are made/reviews needed, calls before deadlines to check in  
  - Response expectations:  
    - Try to respond/acknowledge the message same day  
    - 6 PM onwards, not expected to respond same day  
    - Actually respond within \~1 ”work” day  
- Punctuality and attendance:  
  - If you cannot attend class, or a meeting, let everyone know before the class/meeting time  
- Preparedness for meetings:  
  - Agenda from last meeting  
  - Complete the actionable items from previous minutes
- Engagement  
  - Everyone should participate in discussions  
  - Everyone needs to participate in making decisions  
- Minutes/Note taking, decisions, action items, whom and when  
  - Ian and Nash: minutes record action items/manage project notes etc.  
  - Google Docs informally, Github formally

## Work Distribution

- Where project tasks are defined  
  - GitHub Projects kanban board to track tasks as “issues”, which can be linked to the repository directly  
  - Tasks are categorized as “backlog”, “todo”, “started”, “ready for review”, “done”, or “won’t do”  
- Process for picking tasks and tracking current tasks   
  - Assign issue owners every week during meeting,   
  - People can assign themselves to unassigned tasks during the week  
- How to distribute equally  
  - During meeting, try to give everyone an equal amount of tasks, but  
  -  Consider other coursework / stuff going on in people’s lives in a given week  
  - Also consider difficulty of task / newness of task  
  - Consider all aspects of the project during work distribution

## Commitment to avoid inappropriate behavior, how we will manage conflict

- Talk it through \- don’t hold grudges  
- If text gets ugly or does not resolve issues, do a call or move it to in-person  
- If there is repeated behaviour that the group has a problem with, talk to the person (warning etc) *before* taking it to the prof  
  - If the behavior continues, take it to the prof  
- Inappropriate behaviour in this context:  
  - Anything that wouldn’t be appropriate in a work environment  
  - If you want human attention, demonstrate human effort \- ie don’t ask people to review AI slop docs/PRs that you haven’t bothered to look at  
  - Respect people’s time away from the project

## Documentation
How, Who documents it, change expected

- Document the code/functions that you are the owner of  
- If you write a function, add a short, descriptive docstring  
- If you expand the project to a new domain / add a new organizational structure, add a .md doc (or add to the [README.md](http://README.md)) so that we remember how it works  
- Try to write self-documenting code  
- If you edit something that impacts docs, update the documentation  
- Point of docs:  
  - Explain the purpose of a thing / why it is the way it was  
  - Explains how to use the thing

## Other Ground Rules

### AI expectations  
- To be used as a tool and not a solution  
- Understand what you write  
- Don’t give agents too much access to the project or project details

### Git practices  
- Pull main before you branch  
- 1 branch \= 1 issue  
- Don’t touch files you don’t need to  
- Do lots of atomic commits

### Testing Practices  
- Test-driven development \- write tests first  
- Unit testing, CI, etc

### Values/things that are important to us

- Ask for help when you need it – Don’t be an asshole when to the person asking for help  
- Clear, frequent communication  
- Try not to do stuff last minute  
- Quality of work  
  - Keep code simple wherever possible  
  - Your code works  
  - No shortcuts  
  - Doing the right way  
  - Readable names in code  
  - A bad PR is…  
    - Filled with errors  
    - Too many lines of code  
    - Not following established organization  
- Rest is important
